1. Direct answer

What this project is, in one clear statement.

Yes, the AI backend of this project is developed as an Agentic RAG architecture. It is not just a chatbot with memory. It is a graph-based agent system that can classify the message, choose a route, decide whether retrieval is needed, reformulate the search query when retrieval is weak, call tools when action is required, reflect on its own draft, pass the result through a deterministic safety gate, and finally learn from the exchange by writing back into memory.

RAG part

The system retrieves relevant memories before generating a reply. Those memories include user facts, conversation summaries, emotional history, and persona behavior memory.

Agentic part

The system is not locked into one linear retrieval path. It has route decisions, loops, tool use, reflection, and bounded retries.

Companion part

The system is tailored for AI companion behavior: persona rules, emotional understanding, continuity over time, and strong safety boundaries against dependency and manipulation.

2. How it is built as Agentic RAG

The architecture is created by combining six design decisions inside ai-agent-platform-backend.

Design decision What it does Why it makes the system agentic
LangGraph workflow Organizes the runtime as nodes and conditional edges instead of one request handler. The system can branch and loop instead of always executing one fixed pipeline.
Route selector Picks one of four runtime paths: crisis, direct, retrieve, or tool. The agent first decides what kind of reasoning is needed.
Corrective retrieval Plans the search query, retrieves memories, grades relevance, and reformulates when needed. The agent evaluates retrieval quality and corrects itself instead of trusting the first search.
Tool loop Lets the model request tools, observe tool results, and continue reasoning. The system can act, not only generate text.
Reflection loop Runs a critic pass on the draft to judge grounding, persona fit, and emotional alignment. The agent can judge its own output before final delivery.
Write-back memory learning After replying, the system extracts durable facts, deduplicates them, and updates exact facts in place. The agent improves future responses from prior turns.
Simple mental model A normal RAG app is usually "retrieve once, generate once". This project is "understand, choose path, retrieve if needed, fix retrieval if weak, use tools if needed, generate, critique, safety-check, learn".

4. Main LangGraph workflow

This is the actual runtime graph compiled in ai-agent-platform-backend/graph/workflow.py. The important thing is not only the nodes, but the decision points and loops.

Diagram 2. This is the full reasoning graph. The most important idea is that three separate loops exist inside one workflow: retrieval correction, tool use, and reflection.

What the graph is doing conceptually

The workflow first understands the message, then decides which route to take. If the turn is casual and simple, it can skip retrieval. If the turn needs memory grounding, it enters the retrieval loop. If the turn needs action or external data, it enters the tool loop. After drafting a response, it runs through reflection, then safety, then optional finalization and memory write-back.

5. The four routes

The router is the first major agentic decision. It decides what kind of turn the system is handling.

Route 1: direct

When it is used: casual small-talk or messages that do not need memory or tools.

Path: input -> intent -> emotion -> router -> agent_loader -> context_builder -> prompt_builder -> llm -> reflect -> safety -> response_finalizer -> writeback

Why it exists: not every message should pay the retrieval cost.

Route 2: retrieve

When it is used: questions and emotional turns that benefit from user memory or conversation continuity.

Path: same as direct, but with the corrective retrieval loop inserted before context building.

Why it exists: this is the main memory-grounded conversational path.

Route 3: tool

When it is used: reminders, activity suggestions, web lookups, or profile-dependent actions.

Path: retrieve first, then go from prompt_builder into tool_agent and tool_executor.

Why it exists: some requests require doing something, not just talking about it.

Route 4: crisis

When it is used: self-harm or suicide-risk language.

Path: input -> intent -> emotion -> router -> crisis_response -> safety -> end

Why it exists: crisis handling should not depend on normal generation, retrieval, or persona improvisation.

6. Corrective retrieval loop

This is the strongest RAG-specific part of the architecture. Retrieval is not done once and blindly trusted.

Diagram 3. Retrieval is a closed loop, not a single call. The workflow can search again with a better query.

How the search query is planned

plan_query() strips filler words and keeps salient keywords. If the message is too short, it falls back to the original text so the query is never empty.

When a retry is needed, reformulate_query() broadens progressively. First it tries the full original message, then it enriches the query with intent and emotion hints.

How relevance is judged

The retriever assigns each hit a normalized relevance score in the range 0.0 to 1.0. The grade is sufficient when at least one hit clears the relevance threshold. Otherwise it is insufficient and the loop can continue.

Why this matters This is exactly where the architecture stops being naive RAG. Instead of assuming the first retrieval is correct, the system reasons about retrieval quality.

7. Tool loop and reflection loop

After memory grounding, the system still has two more agentic behaviors: acting through tools and judging its own answer.

Diagram 4. The workflow can act first, then answer, and it can critique its own draft before the final safety gate.

Built-in tools

  • set_reminder for reminder scheduling.
  • suggest_activity for mood-aware suggestions.
  • fetch_user_profile for profile data from the main backend.
  • search_web for real-time facts, but only if configured.

The tool registry exposes schemas to the LLM and ensures that even unknown or failing tools return safe observations instead of crashing the graph.

Reflection behavior

The critic model checks three things: grounding in retrieved memories, persona consistency, and emotional responsiveness. If the draft is weak, the verdict becomes revise and the graph loops back to retrieval and generation.

This reflection layer is fail-open. If the critic is unavailable, the workflow still continues. Safety is the real final gate.

8. How memory works

Memory is implemented as a hybrid architecture: vector memory for fuzzy semantic recall and structured memory for exact facts.

Diagram 5. Vector memory and exact memory serve different purposes. The write-back layer decides what belongs where.

Vector memory

ChromaDB stores embeddings for long-term memory across four collections:

  • user_memory
  • conversation_memory
  • emotional_memory
  • agent_behavior_memory

Each record is tagged with user_id and agent_id, so memory is isolated per user-agent pair.

Exact canonical memory

The SQLite canonical fact store is used for single-valued facts. This avoids contradictions like storing multiple current locations for the same user. If the user says "I moved to Kandy", the canonical location value is updated in place.

How retrieval scores are produced

The retriever combines dense semantic similarity with lexical BM25 reranking:

relevance = alpha * dense_score + (1 - alpha) * lexical_score

The default alpha is 0.7, so meaning matters more than keyword overlap, but exact terms still help when they are important.

How write-back decides what to store

The system does not save everything. It builds candidates from a summary and extracted facts, then decides:

  • skip when the fact is low-value or a near duplicate,
  • insert when the fact is genuinely new,
  • update when a canonical fact changed and should replace the previous value.

This keeps memory useful, smaller, and more internally consistent.

9. How the response is created

The final response is produced in layers. Each layer adds control, grounding, or safety.

  1. Agent configuration is loaded. The system gets persona configuration from the main backend and merges it with the local behavior.txt for the selected agent.
  2. Context is assembled. The system brings together intent, emotion, canonical facts, retrieved memories, and the current message.
  3. A structured prompt is built. The prompt includes sections like [PERSONA], [BEHAVIOR RULES], [KNOWN FACTS], [USER MEMORY], [CONVERSATION MEMORY], [EMOTIONAL MEMORY], [USER MESSAGE], and [TASK].
  4. The model router chooses a provider. OpenAI is preferred for higher quality, Gemini is fallback, and the router can also choose a tool-capable generation path.
  5. The response is drafted. Either the plain llm node generates the reply, or the tool_agent node loops through tool calls before finalizing a draft.
  6. The draft is reflected on. A critic checks grounding, persona fit, and emotional sensitivity. If the answer is weak, the workflow can revise.
  7. The answer is safety-checked. Crisis, manipulation, dependency language, isolation behavior, and identity deception are detected by deterministic rules.
  8. The final text is returned. If the response is empty, the finalizer inserts a fallback supportive response.

What makes the response feel consistent

The companion does not answer from the current message alone. It answers from a composed context that includes persona instructions, exact facts about the user, semantically relevant long-term memories, conversation continuity, emotional signals, and safety rules.

Prompt shape used by the system

persona prompt

[BEHAVIOR RULES]
persona behavior rules

[KNOWN FACTS]

[USER MEMORY]
relevant user facts

[CONVERSATION MEMORY]

10. Agent state and observability

The graph works because every node reads and writes one shared state object.

Key state fields

  • intent and emotion from early understanding.
  • route for the chosen path.
  • search_query, retrieved, and relevance_grade for retrieval control.
  • tool_calls, tool_results, and tool_iters for ReAct.
  • reflection, reflect_verdict, and reflect_iters for self-critique.
  • trace for decision-by-decision observability.

Why the trace matters

The workflow appends a trace entry at major decision points. That means a debug request can show not only the final answer, but the reasoning path: which route was chosen, how many retrieval attempts happened, whether tools were used, whether reflection requested a revision, and whether safety rewrote the answer.

Run metrics collected by the system

The observability layer summarizes the completed run into route, intent, emotion, loop counts, tools used, LLM provider, safety status, trace length, and latency. That makes it easier to evaluate the agent system as an engineered workflow instead of a black box.
