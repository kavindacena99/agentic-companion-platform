0 · The whole flow — one diagram

One message in, one safe reply out — the full pipeline plus the three external systems it talks to.

How to read it: the centre column is the linear LangGraph pipeline (nodes 1–11) that every message walks through, top to bottom. The left rail groups the nodes into phases. The three white boxes on the right are the only external systems agent-core talks to: it fetches persona config from the Main Backend (node 4), reads relevant memories before generating (node 5) and writes new ones after (node 11), and calls a model through the LLM Router at exactly one place (node 8). Every remaining step is deterministic and in-process. The sections below zoom into each part.

1 · The big picture

agent-core is a standalone “AI brain” service. It knows nothing about users, billing, or auth.

agent-core is a separate Django project whose only job is: given one user message, produce one in-character, safe, memory-aware reply. It is deliberately isolated from the product:

  • It has no user accounts, no JWT, no payments — those live in the Main Backend (companio-main-backend).
  • It exposes essentially one real endpoint, POST /chat/, which is AllowAny (an internal service call, not a public API).
  • Its own Django DB is a throwaway SQLite file. The important storage — long-term memory — lives in a ChromaDB vector store on disk.

Where it sits

react-frontend ──JWT──▶ companio-main-backend ──HTTP──▶ agent-core (this service)

Two backends depend on each other at runtime, in opposite directions:

  • Main → agent-core: forwards a chat turn to POST /chat/.
  • agent-core → Main: calls back GET /api/agents/<id>/ to fetch that agent’s persona config (the agent loader).
Reality check on the wiring Today the Main Backend’s real chat flow still uses a mock/legacy path. agent-core is reachable only through the thin testing gateway POST /api/v1/chat/. So this document describes a fully-built engine that is not yet the production default — connecting it is the pending integration step.

2 · The one endpoint & its contract

api/chat.py → services/chat_service.py → the graph.

Everything enters through a tiny DRF view. It validates the payload with a Pydantic model and hands off to the service layer. It never leaks internals — any pipeline error becomes a generic 503.

# POST /chat/  — request
{
  "user_id":    "42",
  "agent_id":   "best_friend",   # must match a folder in agents/ AND an Agent.key in Main
  "session_id": "sess-abc",
  "message":    "my name is Kavinda and I'm learning AI, but I feel exhausted"
}

# 200 — response (deliberately minimal)
{
  "response": "...",     # the final, safety-checked reply
  "emotion":  "stressed",
  "intent":   "emotional"
}

The service function is only a few lines — it runs the graph and shapes the output:

def process_chat(message: ChatMessage) -> dict:
    final_state = run_workflow(
        user_id=message.user_id, agent_id=message.agent_id,
        session_id=message.session_id, message=message.message,
    )
    return {
        "response": final_state.get("response", ""),
        "emotion":  final_state.get("emotion"),
        "intent":   final_state.get("intent"),
    }

So all the intelligence is inside run_workflow — the LangGraph pipeline. That is what the rest of this page unpacks.

3 · AgentState — the shared brain

graph/state.py — one TypedDict that flows through every node.

LangGraph works by passing a single state object between functions. Each node reads the fields it needs and returns a partial update; LangGraph merges that update back into the state and passes it to the next node. AgentState is that object, organized in layers that mirror the pipeline:

LayerFieldsFilled by
Inputuser_id, agent_id, session_id, messagethe request
Understandingintent, emotionclassifier nodes
Agentagent_configagent loader node
Memoryuser_memory, conversation_memory, agent_memorymemory retriever node
Contextcontext (merged dict)context builder node
Promptpromptprompt builder node
OutputresponseLLM node, then safety/finalizer
Safetysafety_flagsevery node can raise a flag; safety node scores
Learningmemory_updateswriteback node
The golden rule of this graph Every external call (memory, agent config, LLM) is wrapped in try/except. A failure sets a safety_flag and returns empty data — it never crashes the graph. The user always gets some reply.

4 · The 11-node pipeline

graph/workflow.py — a single linear StateGraph, compiled once and reused.

This is the heart of the system. The message walks through eleven nodes, START → END, each one enriching the state. Colours group the nodes by responsibility.

1

input input_node

Trims the message, checks required fields are present. Flags empty_message / invalid_input if not.

2

intent intent_node

Classifies why the user is speaking → question / emotional / casual / crisis. A crisis intent immediately raises a safety flag.

3

emotion emotion_node

Detects how the user feels → happy / sad / stressed / neutral.

4

agent_loader agent_loader_node

Loads the persona: fetches config from the Main Backend and merges the local behavior.txt. On failure → agent_unavailable flag, empty config, graph continues.

5

memory_retriever memory_retriever_node

The RAG retrieval step. Similarity-searches all four ChromaDB collections scoped to this user+agent, top-5 each.

6

context_builder context_builder_node

Merges everything the prompt needs — persona, behavior rules, safety rules, intent, emotion, message, and all retrieved memories — into one context dict.

7

prompt_builder prompt_builder_node

Assembles a structured, sectioned prompt string ([PERSONA], [USER MEMORY], …). No LLM call here — just text assembly.

8

llm llm_node

The only place a model is called. Hands the prompt to the LLM router, which picks a provider and generates text. Crisis turns request the highest-quality provider.

9

safety safety_node

The post-LLM gatekeeper. Scores the reply; rewrites or replaces it if it detects crisis, manipulation, dependency, or isolation.

10

response_finalizer response_finalizer_node

Guarantees a non-empty, clean reply — falls back to a gentle default if everything upstream produced nothing.

11

writeback writeback_node

The learning loop. Summarizes the exchange, extracts durable facts, and stores new memories in ChromaDB — so next time the agent remembers.

In code, the wiring is just a straight chain of edges:

builder.add_edge(START, "input")
builder.add_edge("input", "intent")
builder.add_edge("intent", "emotion")
# … agent_loader → memory_retriever → context_builder → prompt_builder …
builder.add_edge("prompt_builder", "llm")
builder.add_edge("llm", "safety")
builder.add_edge("safety", "response_finalizer")
builder.add_edge("response_finalizer", "writeback")
builder.add_edge("writeback", END)
workflow = builder.compile()   # compiled once at import, reused for every request
Why a graph instead of one big function? Each step is isolated, independently testable, and swappable. The state contract makes data flow explicit, and LangGraph gives you a place to later add branching (e.g. skip the LLM entirely on a crisis) without rewriting the flow.

5 · Understanding — intent & emotion

services/classifiers/ · deterministic · no LLM

Before spending money on an LLM, the system cheaply figures out what kind of message this is. Both classifiers are pure rule/keyword matching — fast, free, and predictable.

Intent — why they’re talking

Priority-ordered, so a safety signal is never masked:

  1. crisis — self-harm / suicide patterns (checked first)
  2. emotional — “sad”, “lonely”, “heartbroken”…
  3. question — ends with “?” or “how/what/why…”
  4. casual — the default

Emotion — how they feel

Distress outranks positivity, so mixed messages read as the harder feeling:

  • sad → “down”, “empty”, “hurt”…
  • stressed → “overwhelmed”, “deadline”, “burnout”…
  • happy → “great”, “excited”, “grateful”…
  • neutral → the default

These two labels do real work downstream: intent = "crisis" routes to the strongest LLM and triggers a crisis safety substitution; the detected emotion is injected into the prompt and stored as emotional memory.

6 · Persona — the agent loader

services/agent_loader.py · HTTP · file I/O

There are no hard-coded agents. A persona is assembled at request time from three independent sources, merged into an AgentProfile:

SourceProvidesWhere from
Main Backend configidentity, display_name, persona_prompt, safety_rulesGET /api/agents/<id>/ (HTTP)
behavior.txttone, communication style, boundaries, behavioral ruleslocal file agents/<id>/behavior.txt
safety ruleswhich safety policies applycarried on the backend config

The behavior file is plain text a non-engineer can edit. For example, the Best Friend agent’s file says:

TONE
- Warm, casual, and upbeat. Talk like a close friend, not an assistant.
BOUNDARIES
- Be supportive, never romantic or flirtatious.
- Do not give medical, legal, or financial advice; gently suggest a professional.
Fail-open on config, fail-closed on disable A missing behavior.txt just yields an empty string (no crash). A missing Main Backend is flagged and the graph continues with an empty persona. But an explicit enabled: false raises AgentDisabledError — a disabled agent is intentionally refused.

7 · Memory & RAG (ChromaDB)

memory/ · this is what makes the companion remember you.

This is the “R” and “A” of RAG — Retrieval-Augmented Generation. Instead of stuffing the whole chat history into every prompt, the system stores memories as vectors and retrieves only the few most relevant ones for the current message. Memory is split into four collections:

user_memory

Durable facts & preferences — name, job, what they’re learning, likes/dislikes.

conversation_memory

Summaries of past exchanges, for continuity across sessions.

emotional_memory

Mood events & emotional patterns over time.

agent_behavior_memory

Behavior / personality / tone chunks tied to the agent.

How retrieval works (node 5)

For the incoming message, get_relevant_memories queries each collection and returns the closest matches — always filtered by user_id and agent_id so memories never leak across users or personas:

memories = get_relevant_memories(
    query=state["message"],
    user_id=state["user_id"], agent_id=state["agent_id"],
    top_k=5,
)
# Chroma filter built per query — scoping is enforced, not optional:
where = {"$and": [{"user_id": user_id}, {"agent_id": agent_id}]}

The storage engine

  • ChromaDB persistent client (chroma_client.py) — one lazily-created client, on-disk at CHROMA_DB_PATH.
  • Cosine distance collections (collections.py), matching unit-normalized embeddings.
  • Writer (memory_writer.py) — embeds content and stamps every record with user_id, agent_id, timestamp, memory_type so it’s always filterable.
Embeddings are a placeholder today embeddings.py ships a deterministic hash-based pseudo-embedding (SHA-256 → 256-dim unit vector), not a real semantic model. It makes the memory engine fully functional offline with zero API cost, and identical text always maps to the identical vector. It’s designed behind an interface so a real embedding provider (e.g. OpenAI) can be dropped in later without touching the writer or retriever. Until then, “similarity” is closer to fuzzy text identity than true semantic meaning.

8 · Prompt building

prompt_builder_node · no LLM — pure text assembly

Node 7 turns the merged context into a single, clearly-sectioned prompt. Empty sections are skipped, so the model only sees what’s relevant:

[PERSONA]
<persona_prompt from Main Backend>

[BEHAVIOR RULES]
<contents of behavior.txt>

[USER MEMORY]
- User's name is Kavinda
- User is learning AI

[CONVERSATION MEMORY]
- Conversation summary (emotional tone: stressed). Latest user focus: …

[EMOTIONAL MEMORY]
- User expressed feeling stressed.

[UNDERSTANDING]
Detected intent: emotional
Detected emotion: stressed

[USER MESSAGE]
my name is Kavinda and I'm learning AI, but I feel exhausted

[TASK]
Respond in character, honoring the persona, behavior rules, and the user's emotional state.

This structured layout is what lets a general LLM behave like a specific, memory-aware companion.

9 · The LLM router

llm/llm_router.py · the central brain that picks a model.

Every model call in the system goes through one router. It chooses a provider based on the request’s needs and falls back automatically if the preferred one is missing or errors.

SituationProvider order
High quality needed (or intent == "crisis")openai → gemini
Low-cost preferredgemini → openai
Defaultopenai → gemini
for name in order:
    provider = self.providers.get(name)
    if provider is None or not provider.is_available():
        continue                          # no API key / SDK not installed → skip
    try:
        text = provider.generate(prompt, **kwargs)
        return {"provider": name, "response": text, "ok": True}
    except Exception:                      # any failure → try the next provider
        continue
# nothing worked → safe fallback text, ok=False (still no crash)

Each provider (openai_provider.py, gemini_provider.py) implements a tiny LLMProvider interface — generate() and is_available(). The SDK and API key are resolved lazily, so importing a provider never makes a network call and is_available() is always safe to probe. Adding a third provider (e.g. Claude) is just one new class.

Graceful degradation, end to end No key configured? The provider is skipped. All providers down? The router returns a warm fallback line (“I’m having trouble responding right now, but I’m still here…”). The user is never shown a stack trace.

10 · The safety gatekeeper

safety/engine.py + graph/safety_node.py · deterministic · runs after the LLM

The LLM is never trusted to be safe on its own. After generation, a deterministic, stateless engine inspects the reply and can override it. Design principle: never depend on an LLM to enforce safety.

What it checks

CheckLooks forAction
Crisisself-harm / suicide language in the user messageReplace reply with a supportive, advice-free crisis message
Emotional dependency“you’re all I have”, or AI saying “you only need me”Rewrite
Manipulationguilt/control language in the replyRewrite
Isolation“cut off your friends”, “leave your family”Rewrite
False identity“I’m a real human”, “we can meet in person”Rewrite

How the decision is made

The engine computes a safety score starting at 1.0 and subtracting penalties for each harm found. If crisis is detected the reply is replaced outright; otherwise if the score falls below the threshold (or manipulation/dependency is present) the reply is rewritten — unsafe sentences are stripped and a grounding statement is appended:

# graph/safety_node.py — the gate
if crisis:
    final_response = engine.build_crisis_response()          # full replacement
    safety_flags["rewrite_reason"] = "crisis"
elif response and (manipulation or dependency or score < threshold):
    final_response = engine.rewrite_unsafe_response(response)  # strip + ground

The grounding statement always reminds the user the companion is an AI, not a substitute for real relationships — the core ethical stance of the product baked into code.

11 · Learning — memory writeback

memory/writeback/ · the final node, runs after the reply is decided.

This is what makes the agent get to know you over time. Once the reply is finalized, node 11 learns from the exchange in four deterministic steps:

A

Summarize summarizer.py

Condense the exchange into one short summary line (with emotional tone) → stored in conversation_memory.

B

Extract facts fact_extractor.py

Regex patterns pull durable facts: “my name is ___” → User's name is Kavinda; “I’m learning ___” → User is learning AI. Plus an emotional note if non-neutral.

C

Classify memory_classifier.py

Route each fact to the right collection by its type — user_fact → user_memory, emotional → emotional_memory, etc.

D

Store memory_writer.py

Embed & persist into ChromaDB with full metadata. Returns a list of what was written (memory_updates).

Next time this user messages this agent, node 5 will retrieve these exact memories — closing the loop that turns a stateless LLM into a companion with continuity.

Cheap and reliable by design Summarizer, fact extractor, and classifier are all deterministic (no LLM), so learning from every turn is fast and free. Each is behind a clean seam, so a future step can upgrade any one of them to an LLM-powered version without touching the engine. There’s also an aprocess_writeback async wrapper ready for offloading this work.

12 · How LangGraph & LangChain actually fit

The honest answer — because you specifically asked about both.

LangGraph — actively used

LangGraph is the orchestration engine. The entire pipeline is one StateGraph(AgentState):

  • add_node(name, fn) registers each step
  • add_edge(a, b) defines the linear flow
  • compile() builds a runnable graph (once, at import)
  • workflow.invoke(initial_state) runs one message end-to-end

It handles passing & merging AgentState between nodes. That’s the whole “agentic” machinery here.

LangChain — declared, not used (yet)

langchain is listed in requirements.txt under “AI stack (reserved for later steps)”, but a full-codebase import scan shows it is never actually imported. The only graph library in use is langgraph.

The LLM providers call the OpenAI and Gemini SDKs directly — no LangChain chains, prompts, or model wrappers. So today LangChain is a reserved dependency, not a working part of the flow.

So, precisely: When an agent finds a response, LangGraph drives the step-by-step flow and state, while the actual generation is a direct SDK call inside llm_node → llm_router → provider. LangChain plays no runtime role at present.

Another thing worth naming: this is a graph, but currently a purely linear one — no conditional edges, no loops, no tool-calling agent. The “agentic” behavior (deciding to comfort, ask follow-ups, etc.) is expressed through the prompt + persona + safety layers, not through dynamic graph branching. The structure is clearly set up to add real branching later (e.g. short-circuit to the crisis response and skip the LLM).

That is the whole product promise, realized in one pass through the graph.

14 · Special design choices worth knowing

ChoiceWhy it matters
Deterministic-first — intent, emotion, fact extraction, summarizing, and safety are all rule-basedFast, free, testable, and predictable. The LLM is used only for the one thing it’s uniquely good at: generating the reply.
Safety runs after the LLM, deterministicallyThe model can’t talk its way past the safety layer. Crisis handling never depends on the model behaving.
Never-crash graph — every external call is wrappedMemory down, agent config unreachable, all LLMs failing — the user still gets a coherent reply.
Provider-agnostic LLM layer with lazy loading + auto-fallbackSwap or add models without touching the pipeline; missing keys degrade gracefully instead of erroring.
Memory scoped by user + agent on every read and writeHard isolation — one user’s memories can never surface for another, and each persona keeps its own memory of you.
Config-driven personas (Main config + behavior.txt)New agents need no code — a DB row plus a text file. Non-engineers can tune tone.
Clear seams for upgrades — embeddings, summarizer, classifiers all behind interfacesThe placeholder embedding and rule-based writeback can each become LLM/vector-model powered later without a rewrite.
Two things to fix before production (1) The embedding function is a hash placeholder — real semantic retrieval needs a genuine embedding model. (2) The /chat/ endpoint (and the Main Backend’s /api/v1/chat/ gateway) are AllowAny with no service-to-service auth — that must be tightened before this handles real traffic.
