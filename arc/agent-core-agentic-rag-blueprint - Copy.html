1 · The 6 principles of Agentic RAG

One idea underneath all of them: the LLM drives the process, instead of being a single step inside a fixed script.

PrincipleWhat it meansToday
1. Decide to retrieveThe agent judges whether this turn even needs memory/knowledge — trivial chit-chat shouldn’t hit the vector store.Always retrieves
2. Plan & reformulate the queryThe agent rewrites the raw message into a good search query, and can try again with a better one.Uses raw message
3. Grade & self-correctIt checks whether retrieved memories are actually relevant/sufficient and loops back if not.Uses hits as-is
4. Use toolsIt can call functions (reminders, activity suggestions, lookups) — acting, not just talking.Text only
5. Reflect on its answerBefore replying, it critiques its own draft for groundedness and persona fit, and can revise.No reflection
6. Dynamic control flowBranches and loops in the graph — different messages take different paths.Strictly linear
What stays the same Everything already built stays: the LangGraph runtime, ChromaDB, the provider-fallback LLM router, the deterministic safety engine, and the write-back loop. Agentic RAG is about adding decisions, loops, and tools around that spine — not replacing it.

3 · The agent orchestrator — LLM as controller

The single biggest shift: promote the LLM from “a step” to “the decision-maker.”

In the current design the model is called once, near the end, to write a reply. In Agentic RAG the model is consulted several times to make control decisions — should I retrieve? is this good enough? do I need a tool? is my answer grounded? LangGraph is the perfect host for this because a graph can branch and loop based on those decisions.

Decision calls (cheap model)

Small, structured LLM (or classifier) calls that return a label/JSON: route, relevance grade, tool choice, reflection verdict. Fast and cheap.

Generation call (strong model)

The one expensive call that writes the actual reply — still routed through the existing provider-fallback llm_router.

Cost is controlled, not blown up More LLM calls sounds expensive, but the decision calls are tiny and often skip the whole retrieval/tool machinery (e.g. casual turns answer directly). A crisis turn can bypass the LLM entirely. Net effect: spend compute only where it helps.

4 · The agentic control graph

The centrepiece: a graph with a router, two self-correcting loops, a tool loop, and a crisis fast-path.

crisis fast-path direct answer (no retrieval) corrective-retrieval loop tool loop self-reflection loop
Diagram B — the agentic graph. Solid grey = the happy path; coloured/dashed = decisions, branches and loops (the “agentic” part). Every message takes a different route.
Guardrail: bound the loops Any looping agent needs limits. Cap the retrieval-reformulation and reflection loops (e.g. max 2–3 iterations) and use LangGraph’s recursion limit, so a hard question degrades to “best effort so far” instead of spinning forever.

5 · Agentic query routing

The first fork: not every message deserves the full machinery.

A lightweight router (the deterministic classifiers you already have, optionally backed by a small LLM call) picks one of four paths:

RouteExamplePath taken
crisisself-harm signalsStraight to the deterministic crisis response → safety → end. The LLM is never called.
direct“haha good morning!”Skip retrieval, generate a persona reply directly.
retrieve“remember what I said about my exam?”Enter the full plan → retrieve → grade loop.
tool“remind me at 8pm”Route to the tool executor, then generate.

This alone delivers principle #1 (decide to retrieve) and #6 (dynamic flow) — and it makes the system cheaper and safer at the same time.

6 · Self-correcting retrieval loop

The signature move of Agentic RAG: retrieve, grade what you got, and try again if it’s weak.

Diagram C — corrective retrieval. A relevance grade decides whether to proceed or loop back with a reformulated query (bounded by a max-iteration cap).

Concretely this needs three additions to the existing memory/ layer: a query planner (rewrite the message into a search string), a relevance grader (score/verify the returned memories), and hybrid retrieval (semantic vector search combined with metadata filters and optional re-ranking).

7 · The tool-use layer

Let the agent act — reminders, activity suggestions, profile lookups — not just talk.

Diagram D — the tool loop (a.k.a. ReAct): decide → execute → observe → feed the result back into generation, repeat until no tool is needed.

Each tool is a typed function with a name, description, and schema — exposed to the model via function/tool calling. Companio-relevant tools: set_reminder, suggest_activity, fetch_user_profile (from the Main Backend), search_web. The safety engine still runs on the final text, unchanged.

8 · Generation + self-reflection

Before the reply leaves the model, the agent grades its own draft.

A reflection step asks a cheap model a focused question: “Is this draft grounded in the retrieved memories, consistent with the persona, and responsive to the user’s emotion?” If not, it loops back — to reformulate retrieval or to regenerate — up to the iteration cap. This catches hallucinations and off-persona replies before the deterministic safety gate, which remains the final, non-negotiable check.

Two distinct guards, in order ① Reflection (LLM, quality & groundedness — can loop) → ② Safety engine (deterministic, ethics & crisis — always runs, never trusts the model). Reflection improves the answer; safety guarantees it can’t be harmful.

9 · How user memory works & agentic write-back

User memory is why the companion feels personal — it’s what lets an agent remember you across sessions.

User memory is the store of durable facts about a person — their name, what they’re studying, their job, likes/dislikes, goals, and important life events. It is one of the four memory collections, and it’s the one that makes conversations feel continuous: the agent can reference something you said days ago because it was written to user memory and retrieved again later.

The lifecycle — written once, recalled forever

User memory follows a simple loop that spans separate chat sessions: facts are extracted and stored during one conversation, then semantically retrieved and injected into the prompt in any future conversation with the same agent.

Diagram E — the user-memory lifecycle. Facts written in one session survive in ChromaDB and are semantically retrieved into any later session with the same agent, scoped strictly by user_id + agent_id.

What a user-memory record looks like

Each fact is stored as an embedded document with metadata that makes it filterable and, in the agentic version, updatable:

{
  "id":        "3f2a…",
  "content":   "User is learning AI",        # the fact (also embedded to a vector)
  "user_id":   "42",                        # WHO — hard isolation
  "agent_id":  "best_friend",               # WHICH persona remembers it
  "memory_type":"user",                       # user | conversation | emotional | behavior
  "importance": "high",                      # drives retention / ranking
  "timestamp":  "2026-07-17T…Z"             # for recency & conflict resolution
}

Two paths: read (retrieve) and write (learn)

Read — every relevant turn

The user message is embedded and used to similarity-search user_memory, filtered by user_id + agent_id. The top matches are injected into the prompt’s [USER MEMORY] section, so the reply is personalized. In the agentic design this only fires when the router decides the turn needs it.

Write — the agentic upgrade

Instead of the current fixed-regex “store everything,” the agent decides what is worth remembering, deduplicates against existing facts, and resolves contradictions — e.g. “I moved to Kandy” should update the old location fact, not add a duplicate.

decide: store or skip deduplicate update & resolve conflicts importance / decay vector + structured
Isolation is non-negotiable Every read and write is scoped by user_id and agent_id. One user’s memories can never surface for another, and each persona keeps its own view of you — so your Best Friend agent and your Mentor agent remember you independently.
Where user memory fits the bigger picture User memory is one of four collections. conversation_memory holds session summaries, emotional_memory tracks mood over time, and agent_behavior_memory holds persona/tone. For exact, canonical facts (a verified name, birthday, subscription tier) a structured store (graph/SQL) can complement the vector store — vectors for fuzzy recall, a table for precise lookups.

10 · Retrieval foundation — real embeddings first

None of the above is meaningful until retrieval is semantically real.

Prerequisite #0 The current embeddings.py is a deterministic hash placeholder — “similarity” is closer to fuzzy text-identity than meaning. Swap in a real embedding model (OpenAI, or a local sentence-transformer) behind the existing EmbeddingProvider interface before building agentic retrieval on top. It’s a drop-in change the code already anticipates.

With real embeddings in place, add hybrid retrieval (dense vectors + metadata filters, optionally keyword/BM25) and a re-ranker so the grader has high-quality candidates to judge.

11 · The upgraded AgentState

Loops and decisions need a few more fields to carry their working memory.

class AgentState(TypedDict):
    # --- existing ---
    user_id: str; agent_id: str; session_id: str; message: str
    intent: Optional[str]; emotion: Optional[str]
    agent_config: dict; context: dict; prompt: str
    response: Optional[str]; safety_flags: dict; memory_updates: list

    # --- NEW: agentic control & working memory ---
    route: Optional[str]              # crisis | direct | retrieve | tool
    search_query: Optional[str]       # the planned/reformulated query
    retrieved: list                   # candidate memories this iteration
    relevance_grade: Optional[str]    # sufficient | insufficient
    retrieve_iters: int               # loop counter (bounded)
    tool_calls: list; tool_results: list
    reflection: Optional[str]         # accept | revise
    reflect_iters: int
    trace: list                       # decisions taken, for observability

The trace field matters: an agent that makes decisions must be observable, so every route, grade and loop is logged for debugging and evaluation.

12 · Code sketch — loops & conditional edges

The mechanics are small: LangGraph’s add_conditional_edges plus edges that point backward.

def build_agentic_workflow():
    b = StateGraph(AgentState)
    for name, fn in NODES.items():
        b.add_node(name, fn)

    b.add_edge(START, "intake")
    b.add_edge("intake", "router")

    # 1) router fans out to four paths
    b.add_conditional_edges("router", route_decision, {
        "crisis":  "crisis_response",
        "direct":  "generate",
        "retrieve":"plan_query",
        "tool":    "generate",
    })

    b.add_edge("plan_query", "retrieve")
    b.add_edge("retrieve", "grade")

    # 2) grade loops back OR proceeds (bounded by retrieve_iters)
    b.add_conditional_edges("grade", grade_decision, {
        "insufficient": "reformulate",   # → loop
        "sufficient":   "generate",
    })
    b.add_edge("reformulate", "retrieve")   # the cycle

    # 3) generation may loop through tools
    b.add_conditional_edges("generate", tool_decision, {
        "use_tool": "tool_executor",
        "done":     "reflect",
    })
    b.add_edge("tool_executor", "generate")  # observe & continue

    # 4) reflection accepts OR revises
    b.add_conditional_edges("reflect", reflect_decision, {
        "revise": "plan_query",   # → loop
        "accept": "safety",
    })

    b.add_edge("crisis_response", "safety")   # fast-path rejoins here
    b.add_edge("safety", "finalize")
    b.add_edge("finalize", "writeback")
    b.add_edge("writeback", END)

    return b.compile()   # set a recursion_limit when invoking

Each *_decision function reads the state (a grade, a tool request, a reflection verdict) and returns a string key — that’s the entire mechanism that turns the linear pipeline into a reasoning agent.

13 · Migration map — today → target

Reuse everything; add decisions and loops around it.

Today (linear)Becomes (agentic)Effort
hash-placeholder embeddingsreal embedding model (drop-in)Low · do first
intent/emotion nodesa router with conditional edges (+ crisis fast-path)Low
memory_retriever (fixed top-5)plan → retrieve → grade → reformulate loopMedium
llm node (single call)generate + tool loop + reflectionMedium
safety nodeunchanged (still deterministic, final)None
regex write-backagent decides / dedupes / updates memoryMedium
AgentState+ control & trace fields; bounded loop countersLow

Suggested order: ① real embeddings → ② router + crisis fast-path → ③ corrective retrieval loop → ④ reflection → ⑤ tools → ⑥ agentic write-back. Each step is shippable on its own and moves the system measurably closer to Agentic RAG.

14 · Component & tech summary

Keep (already there)

  • LangGraph state-machine runtime
  • ChromaDB vector store · 4 collections
  • Provider-fallback LLM router (OpenAI/Gemini)
  • Deterministic safety engine
  • Config-driven personas (config + behavior.txt)
  • Write-back pipeline scaffolding

Add (for agentic)

  • Real embedding model + hybrid retrieval + re-ranker
  • Router / grader / reflection decision nodes
  • Conditional & looping edges (bounded)
  • Tool registry + function-calling executor
  • Structured memory store (graph/SQL) for exact facts
  • Trace/observability + an eval harness
The takeaway Companio doesn’t need a new system to be Agentic RAG — it needs its existing pieces wired into a decision-making loop. Real embeddings + a routing/grading/reflection layer over the current LangGraph turns “RAG with an agentic-ready architecture” into genuine Agentic RAG.
